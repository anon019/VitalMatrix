# Health 饮食、AI 建议与分享海报优化方案

日期：2026-08-21（2026-09-06 更新 AI 接入）

## 1. 结论与技术选型

### 模型

- 饮食图片识别：Codex CLI `gpt-5.6-luna`，Medium
- 每日综合健康建议与 AI 对话：Codex CLI `gpt-5.6-luna`，Low
- 按需 AI 海报视觉素材：Codex CLI 调用 `gpt-image-2`

当前后台不再持有或直连模型 API Key，统一复用服务器 Codex CLI 登录态。图片输入、结构化输出、建议生成与 GPT Image 文件落盘均已完成真实调用验证。官方模型页：

- <https://developers.openai.com/api/docs/models/gpt-5.6-luna>
- <https://developers.openai.com/api/docs/models/gpt-image-2>

### 海报

按用户确认后的方向，采用“结构化数据模板 → GPT Image 2 生成无文字底图 → 后端确定性排版”的按需方案：

1. 只有用户点击“生成海报”时才通过 Codex CLI 调用 `gpt-image-2`，上传和识图完成后不自动生成。
2. 后端从餐食记录提取固定字段和完整首句；图片模型只生成本餐与未来三餐的视觉底图，全部关键文字由后端排版。
3. 固定输出 3:4、1K 单张海报，不再生成无限长 Canvas；以手机分享清晰度换取更快的首次生成与加载，环境变量仍可切回 2K。
4. 同一餐、同一内容和同一设计版本复用缓存；只有内容变化或 `force=true` 才重新计费。
5. API 同时返回 `verified_metrics`；V9 放大未来三餐区域，后端在本餐主区域确定性绘制四项营养、完整一句话结论以及三餐文字，不再生成底部重复营养页脚。

需要保留一个产品事实：GPT Image 2 只负责视觉底图，模型偶发生成伪文字时应通过提示词和人工评测继续监控；用户可见的标题、营养数字、结论和餐单文字均由后端确定性绘制。

## 2. 实施状态与已修复问题

### 后端模型调用

本次检查前为旧 Preview；当前生产实际配置与生成记录为：

- `AI_PROVIDER=codex`
- `CODEX_MODEL=gpt-5.6-luna`
- `CODEX_VISION_REASONING_EFFORT=medium`
- `CODEX_TEXT_REASONING_EFFORT=low`
- `CODEX_IMAGE_MODEL=gpt-image-2`
- 今日建议：`model=gpt-5.6-luna`、`prompt_version=recommendation-v2.2`

全部 AI 主链路均通过临时隔离工作目录执行 Codex CLI；文本与识图任务禁用技能和文件写入，图片任务只允许写入单次临时目录。

### 饮食图片分析

本轮已处理的问题：

- 提示词要求“识别准确率 > 90%”和“重量误差 < 20%”，但单张照片无法保证，容易制造虚假精确。
- 每次识图默认联网搜索两餐菜谱，延迟和失败面明显增加，且菜谱内容盖过本餐记录本身。
- JSON 结构在提示词中重复且体积大；现已使用 Codex CLI 的结构化输出约束。
- 缺少食物级置信度、热量范围、估算依据和用户确认问题。
- 食谱字段存在契约漂移：后端新结构使用 `next_meal_recipes`，历史小程序仍读取 `next_meals`/`next_meal_menu`。
- 用户画像改为读取真实资料；当前单用户资料为男性、1992 年 8 月出生、82 kg，不再在提示词里硬编码一个通用男性。
- 分析结果经过服务端强结构校验、数值范围校验和营养合计一致性校验；响应记录模型、Schema 版本和是否使用搜索。
- 默认关闭识图联网搜索。基础识别与下一餐建议使用近 7 天餐食上下文；只有需要来源、时令信息或用户明确要求具体菜谱时才启用搜索。

### 综合 AI 建议

已把输出优先级调整为饮食、睡眠/恢复、活动/训练，并保留原有 `summary`、昨日回顾、今日建议和健康知识结构。建议记录新增 Prompt 版本与数据完整度；当天缺失时只能显式返回带来源日期的历史建议，指定历史日期不再错误回退。

### 分享海报

当前服务器工作树没有权威 `miniprogram/` 源码；小程序适配必须在 Mac 上实际发布的工程中完成。本轮没有把服务器历史版本恢复为生产来源，完整契约和执行 Prompt 见 `docs/2026-08-21-miniprogram-frontend-adaptation.md`。

已确认的问题：

- 海报把照片、营养汇总、评分、全部食物、全部营养分析、全部洞察、行动清单和完整菜谱塞进一张超长 Canvas，信息密度不适合分享。
- 预览容器 `max-height: 85vh`，但没有 `overflow-y: auto`；超长图片溢出后不能滚动，直接造成“只能看到一半”。
- Canvas 固定逻辑超过 1,500 行，高度先估算再绘制，文本结构变化后很容易被截断。
- 画布逻辑读取 `recommendations.next_meals`，与当前 AI 输出的 `next_meal_recipes` 不一致，内容容易缺失。
- 海报使用大量彩色渐变卡片，视觉层级平均，没有一个清晰的分享主结论。

### Web 页面与性能

Web 已新增完整饮食页和 AI 建议页，并把今日页调整为饮食优先。路由现为懒加载，趋势接口具有 60 秒缓存、并发请求去重和卸载取消保护；Recharts 被拆到独立 vendor chunk。

饮食页现已适配两阶段分析：上传完成立即插入核心识图结果，只轮询 `pending/processing` 餐次，建议完成后局部刷新。未来三餐完整展示份量、热量、蛋白质、食材标签和编号做法；推荐失败可单独重试。餐食图片加载失败会进入占位状态，不再留下空白区域。

餐食原图和缩略图已明确归类为长期个人健康档案，禁止按日期自动清理。历史事故、保留策略和恢复边界见 `docs/2026-08-21-nutrition-pipeline-and-media-retention.md`。

最终生产构建中入口脚本 gzip 60.15 KB，React vendor 17.39 KB，HTTP vendor 18.63 KB；图表独立 chunk gzip 106.54 KB，不再随非图表首屏同步执行。ESLint、TypeScript 和 Vite 构建全部通过。生产依赖审计从 7 项可利用链路修复为 0 项（最终 `npm audit --omit=dev`：0 low/moderate/high/critical）。

## 3. 目标产品结构

### 饮食管理主链路

建议从“一张图直接生成一篇长报告”改为四步闭环：

1. 拍照：提供俯拍、光线、参照物和隐藏食材提示，客户端压缩并显示上传/分析进度。
2. 识别：GPT-5.6 Luna Medium 输出食物、份量、置信度、视觉依据和不确定项。
3. 确认：用户可一键修改食物名称、份量、烹饪方式和漏识别食材；修改结果作为后续评估数据。
4. 行动：展示本餐一个结论、两个优点/短板，以及按时间顺序覆盖未来 24 小时的三顿正餐。详细做法折叠为次级内容。

中期应将营养计算拆成“视觉模型识别食物和份量 + 标准食物成分库确定性计算”。LLM 适合视觉识别与解释，不应长期作为唯一的营养数值数据库。

### AI 健康建议

首页只显示“今日三个动作”：

- 饮食：下一餐最重要的一项调整
- 睡眠：今晚一项可执行安排
- 活动/训练：与恢复状态匹配的强度和时长

展开后再显示数据依据、趋势、不确定性和健康知识。每条建议都要包含“做什么、为什么、依据哪些数据”。如果饮食只记录了一餐，必须显示“基于已记录餐食”，不能按全天总摄入下结论。

### 海报 V2

默认只做一张固定比例的分享卡，本轮固定为 3:4、1K，不再生成无限长报告；需要印刷级导出时可配置为 2K。

固定内容：

- 顶部 45%：原始餐食照片，统一裁切与轻量遮罩
- 餐次与日期
- 热量 + 蛋白质/碳水/脂肪四个核心数字
- 综合评价与置信度标识
- “本餐亮点”一条
- “未来三餐”三个简短标题
- 简短免责声明

不放入海报：完整食物列表、三段长营养点评、风险清单、两餐完整菜谱、模型名称。详情留在小程序落地页。

交互：

- 预览层使用真正的可滚动区域，并为底部操作栏预留安全区。
- “保存图片”“发送给朋友”“重新选样式”固定在底部。
- 提供 2-3 个经过设计的模板，不让用户面对大量风格配置。
- 内容超长时按字段限长和优先级裁剪，不按 Canvas 高度无限扩展。

GPT Image 接入方式：

- 上传餐食、打开详情、点击分享均不调用图片模型。
- 点击“生成海报”后调用 `POST /api/v1/nutrition/meals/{meal_id}/poster`。
- 首次生成返回 `generated=true`；相同内容再次打开返回缓存并标记 `generated=false`。
- 前端以服务端 `poster_url` 为唯一图片来源，并保留 `verified_metrics` 供数字校验。
- 不生成二维码、网址、虚构品牌和额外食物；需要小程序码时由前端或服务端确定性叠加。

## 4. 各页面迭代建议

### 小程序首页

- 从训练中心改为健康行动首页，首屏顺序为饮食记录入口、今日三个动作、昨夜睡眠/恢复、活动与训练。
- 合并首页和 AI 页的重复建议内容；首页摘要，AI 页解释依据。
- 移除“Zone2 分钟 × 固定克数”的脂肪燃烧估算，这类数字容易造成错误确定感。
- 首页所需数据改为一个聚合接口，避免多请求后拼装。

### AI 建议页

- 按饮食、睡眠、活动/训练三个主题分组，每组只突出一个动作。
- 显示“数据截至时间”和数据完整度，避免用户把旧建议当成实时建议。
- 展开项展示证据和限制条件；重新生成按钮显示成本较低的明确反馈，并防重复点击。

### 饮食列表页

- 上传入口固定在首屏，显示今天已记录餐数和数据完整度。
- 每餐卡片只显示照片、餐次、热量区间、蛋白质与置信度；长建议进入详情。
- 加入上传压缩、断点/失败重试、分析中占位和重复上传保护。
- 日汇总区分“已记录摄入”和“目标”，没有完整三餐时不要显示为全天缺口。

### 饮食详情页

- 首屏显示照片、四项核心营养、热量范围和综合结论。
- 支持确认/编辑食物和份量，这是提升长期准确率最重要的功能。
- 不确定项用问答卡呈现，而不是藏在长文本中。
- 建议按优先级折叠；完整菜谱作为可选二级页面。
- 分享入口进入海报模板选择，而不是直接绘制整页。

### 趋势页

- 增加饮食、睡眠、恢复三个顶层视图；训练不再占据绝大多数内容。
- 饮食趋势展示记录完整度、蛋白质、蔬菜/纤维、晚餐时间，而不仅是热量。
- 可展示“晚餐时间与睡眠评分”“酒精/咖啡因记录与睡眠”等探索性关联，但必须标注相关不等于因果。
- 7/30/90 天统一切换，长列表采用分页或按需渲染。

### 设置页

- 允许配置健康优先级、饮食目标、睡眠目标、忌口/过敏、饮食偏好和建议强度。
- 去掉 HR Max 185 等静默默认值；缺失就提示完善资料。
- 明确 Polar/Oura 的同步状态、数据权限和最后成功时间。
- 不在普通用户页面展示后端服务地址。

### Web 总览

- 首屏新增饮食记录完整度、今日营养概览和今日三个动作。
- 评分卡要同时展示变化方向和基线，而不是只展示孤立分数。
- 将各大图表路由懒加载；首页只加载当前可见组件。

### Web 睡眠

- 增加入睡/起床时间、总睡眠、睡眠债、规律性和夜间心率，而不是只展示评分/HRV。
- 将“昨夜发生了什么”和“今晚做什么”置于图表之前。

### Web 恢复

- 解释恢复评分的主要贡献因素，并展示个人基线偏离。
- 将 HRV 与静息心率放在同一恢复语境下，避免重复图表。

### Web 活动

- 增加活动目标进度、久坐中断和日内分布。
- 修正久坐字段的单位契约，避免前端以秒/分钟混用换算。

### Web 压力

- 展示压力与恢复时段，而不仅是累计分钟；提供当天可执行的恢复动作。
- 无数据时解释设备采集条件，而不是只显示空态。

### Web 训练

- 目标应来自用户配置而不是页面硬编码。
- 加入训练负荷与恢复状态的联合提示，避免单纯追逐 Zone2/高强度分钟。

### Web 登录与全局体验

- 完善输入标签、键盘操作、焦点态、错误说明和移动端导航。
- 统一空态、错误态、重试和数据更新时间。
- 引入共享数据缓存（SWR 或 TanStack Query）、请求去重与 AbortController。
- 路由级 `lazy`/`Suspense`，把 Recharts 和非首屏页面拆出主包。

## 5. 实施结果与后续演进

### P0：稳定和纠偏（已完成）

- 将全部 AI 主链路统一为 Codex CLI 与 GPT-5.6 Luna Medium。
- 启用饮食 JSON Schema，加入置信度、热量范围和确认问题。
- 默认关闭识图时的菜谱联网搜索。
- 修正性别硬编码、模型默认值和旧思考参数。
- 输出 Mac 权威小程序源码的完整适配契约与执行 Prompt。
- Web 海报预览已改为完整滚动；小程序对应适配项已进入 Mac Prompt。
- 升级有漏洞的 Web 直接依赖并完成构建回归。

### P1：饮食核心体验与海报 V9（后端与 Web 已完成，小程序待 Mac 适配）

- 上线食物/份量确认编辑。
- 重做饮食详情信息层级和建议卡。
- 完成 3:4 GPT Image 2 按需海报、内容缓存、并发去重、每日额度和超时；V9 默认 1K 渐进式 JPEG，由后端确定性排版全部关键文字并取消重复营养页脚。
- 建立 30-50 张真实餐食的人工校正评测集。
- 记录模型、延迟、token、置信度、用户修正率和失败原因。

### P2：综合健康闭环与性能（本轮已完成主体）

- 首页和 AI 建议按饮食、睡眠、活动三条主线重构。
- 新增饮食/睡眠趋势和数据完整度。
- Web 路由拆包、共享请求缓存、请求取消和图表按需加载。
- 后端将营养数值逐步迁移到标准食物成分库计算。

### P3：持续质量闭环（后续真实样本评测）

- 评测 30-50 张真实餐食海报的中文错字、数值一致性、截断率和视觉质量。
- 关键数字的确定性覆盖层已经上线；继续用真实样本跟踪正文中文和构图稳定性。
- 增加 2-3 套风格、超时、降级、并发去重和内容安全策略。

## 6. 验收指标

- 饮食结构化响应成功率 ≥ 99.5%。
- 所有餐食显示置信度或不确定性；用户可在 3 次点击内修正食物/份量。
- 统计用户修正率，按食物类别分析识别薄弱点，不使用无法验证的“准确率 > 90%”宣传。
- 缓存海报读取 P95 ≤ 1 秒；首次 AI 海报目标 P95 ≤ 20 秒，保存成功率 ≥ 99%。
- 海报核心营养数字与 API `verified_metrics` 一致率 ≥ 99%，所有支持机型可完整预览和滚动。
- AI 建议每次至少包含一条饮食动作和一条睡眠/恢复动作，且明确数据完整度。
- Web 首包 JS 目标 gzip < 120 KB，路由切换不重复请求相同趋势数据。
- 直接依赖高危审计项清零。
