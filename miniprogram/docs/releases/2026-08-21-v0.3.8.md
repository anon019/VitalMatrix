# Mini Program 0.3.8

## 两阶段推荐状态

- 上传识图返回后立即进入详情；当核心分析完成、建议仍在生成时显示“识图完成，饮食建议生成中”。
- 状态接口每 2 秒直接发起请求，不读取也不写入通用 GET 缓存。
- 建议完成后先等待可能存在的详情请求结束，再清理详情缓存并显式强制获取最终内容。
- 建议失败时仅显示“重新生成建议”，普通重试调用独立建议接口且不传 `force=true`，不会重复上传或识图。
- 页面隐藏或销毁时清理定时器；回到仍处于 `pending/processing` 的详情页后重新开始轮询。

## 菜谱展示

- 完整保留 `timing`、`flavor_profile`、`experience_note`、`portion`、`protein`、`ingredients` 和 `cooking_steps`。
- 每道菜使用独立卡片；份量和蛋白质位于菜名下方，食材按标签换行，做法按编号逐条展示。
- 口味特点、体验说明和搭配理由收拢到餐次卡片底部。
- 活动小程序代码已无 `recommendations.next_meals` 读取；当前详情统一使用 `next_meal_recipes`，海报由服务端 `/poster` 接口生成。

## 历史图片

- 列表图片带错误回调；详情图片失败后设置 `imageLoadFailed`。
- 列表和详情均显示“历史图片不可用”占位，不保留空白图片区域。
- 缺失图片在当前 App 会话内按餐食 ID 熔断，不持续请求同一个 404 资源；海报链接的 403 恢复逻辑保持独立。

## 验证

- 本地请求测试确认状态接口连续调用不会命中缓存，强制详情请求会跳过旧详情缓存。
- 状态机测试确认 2000ms 轮询、页面隐藏清理、完成后强制刷新和失败普通重试 `force=false`。
- 字段测试确认七类菜谱字段均进入视图模型并按列表或步骤渲染。
- JavaScript、WXML、WXSS 与 diff 静态检查通过；真实上传后等待三餐自动出现，以及新图片在列表、详情和海报中的端到端显示，仍需开发者工具重新登录后补验。
